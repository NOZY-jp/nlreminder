# nlreminder 開発ルール

本リポジトリで実装・改修を行う **人間・エージェント共通** のルール。**作業開始時に毎回このファイルを読むこと。**

---

## 1. 必読ドキュメント（毎回）

作業を始める前に、少なくとも次を確認する。

| 優先 | ファイル | 用途 |
|------|----------|------|
| 1 | **本ファイル `dev.md`** | 開発プロセス・コーディング規約 |
| 2 | [`_nlreminder.md`](_nlreminder.md) | 要件・設計判断 |
| 3 | [`struct.md`](struct.md) | **型・DB 列の正本** |
| 4 | [`api.md`](api.md) | **関数・rig ツール・LLM 呼び出しの正本** |
| 5 | 触る領域の既存 `src/` コード | 命名・モジュール分割の実態 |

初回 OAuth や Cloud Console 操作時のみ [`prep_manual.md`](prep_manual.md) を参照する。

**仕様（`struct.md` / `api.md`）と実装が食い違う場合:** 意図的でなければ **ドキュメントを正** とし、必要なら先にドキュメントを更新してからコードを直す。

---

## 2. テスト駆動（TDD）

§10.L および §9.5 に従う。

1. **仕様書を読む** — 型は `struct.md`、API は `api.md`
2. **テストを先に書く** — 要件・計画からテストケースを起こす。既存実装に合わせてテストを曲げない
3. **テストが通るように実装する** — テストを通すためだけの過剰設計はしない
4. **`cargo test` を通してから** 作業終了・コミット

### テストの置き場所

| 種類 | 場所 |
|------|------|
| ユニットテスト | 各モジュール末尾の `#[cfg(test)] mod tests` |
| 統合テスト | `tests/`（外部 API は `#[ignore]` + 手元実行） |

### テスト方針

- **時間依存ロジック**は `*_at(now, ...)` のように **時刻を引数で注入**（`default_fetch_range_at`, `adjust_for_quiet_hours_at` 等）
- **外部 HTTP**（Google, CalDAV, Discord, LM Studio）はユニットテストで **スタブ / モック**。実サーバーは `tests/*.rs` の `#[ignore]` のみ
- **LLM 出力**は JSON スキーマ（§9.5）に対するパース・バリデーションをモックデータでテスト
- 自明なテスト（getter の存在確認だけ等）は書かない

---

## 3. モジュール・ファイルの責務

### 分割する

- 1 ファイルに **HTTP・パース・DB・LLM・Discord** が混在したら分割する
- **目安:** 1 ファイル **300 行超** で責務が複数なら分割を検討（厳密な上限ではない）
- レイヤー例:
  - `sync/` — 外部 → DB の同期
  - `models/` — DB 行 ↔ ドメイン型
  - `llm/` — プロンプト・JSON 入出力
  - `discord/` — serenity ハンドラ・Embed 組み立て
  - 外部 API の生呼び出しは **rig ツール / sync の下** に閉じる

### 統合する

- **同じ責務**が複数ファイルに散らばっていたら統合する
- 薄い `mod.rs`（re-export だけ）は維持してよい
- **CLI サブコマンドは増やさない** — LLM / デーモン向け機能は lib API + rig ツール（§9.3, §9.4）。人間向けは `run` と `setup google` のみ

### 新規コードの置き場

- ドメイン型 → `src/models/`（§9.7）
- 既存モジュールの命名・import スタイルに合わせる
- `color_eyre::Result` をエラー型として統一

## 4. 実装の優先順位（MVP）

`_nlreminder.md` §8 の成功基準に向け、おおよそ次の順で進める。

1. DB upsert（CalDAV / Tasks）+ `models`
2. 定期スキャン（デーモン内 tokio タスク）
3. rig ツール + LLM クライアント
4. Discord bot（通知・意図解析）
5. 朝サマリー・リマインド計画・ハートビート

横断的変更（migration, config）が必要なら **そのスライス内で完結** させる。

---

## 5. コミット（Jujutsu）

**作業日の終わり**（または意味のあるスライスが完了した時点）で **jujutsu (`jj`)** を使ってコミットする。

```bash
# 例
jj status
jj diff
jj commit -m "sync CalDAV events into calendar_events table"
```

### コミットメッセージ

- **1 行目:** 変更の目的（英語または日本語、リポジトリ内で統一）
- **本文（任意）:** なぜその方針か。仕様のどの節に対応するか
- `cargo test` 通過後にコミットする
- **`.env` / 秘密情報 / ローカル DB はコミットしない**

`git` ではなく **`jj` を正** とする（リポジトリが jj 運用の場合）。

---

## 6. 変更のスコープ

- **要求された範囲だけ** 変更する。無関係なリファクタ・フォーマット全体は混ぜない
- バグ修正と機能追加を同一コミットにしない（可能なら）
- migration を追加したら **同じ PR / コミット系列** で Rust 側の読み書きも更新する
- 仕様変更は **`_nlreminder.md` を先に（または同時に）** 更新する

---

## 7. 外部連携の作法

| 連携 | ルール |
|------|--------|
| CalDAV | 読取・書込は `sshCalendar`（`caldav_calendar_path`）。§9.8 |
| Google Tasks | `@default` リストのみ |
| Gmail | historyId 増分。初回は 7 日遡及 |
| LLM | rig ツール経由のみ。直接 DB/API を LLM に触らせない |
| Discord | ユーザー投稿のみ意図解析。Embed 枠は Rust、本文は LLM |

エラー時は **スキップして次スキャン**（§9.8）。ユーザー向けに Discord でエラー詳細を垂れ流さない。

---

## 8. 作業終了チェックリスト

- [ ] `dev.md` と `_nlreminder.md` §9 の該当節を読んだ
- [ ] テストを計画どおり追加・更新した（TDD）
- [ ] `cargo test` が通る
- [ ] 秘密情報をコミットしていない
- [ ] 仕様変更があれば `_nlreminder.md` を更新した
- [ ] `jj commit` した（作業日の区切り）

---

## 9. エージェント（Cursor 等）向け追加ルール

- 推測で仕様を変えない。§9.8 の **確定判断** を優先する
- 実装前に **既存コードを grep / read** し、同機能の重複を作らない
- 1 ターンで巨大 diff を避け、**テスト可能な縦スライス** で出す
- ユーザーが「コミットして」と言うまで **勝手に commit / push しない**（`dev.md` §5 は作業日終了時の規範。明示指示がある場合はそれに従う）
- 調査だけの依頼では **コードを変更しない**
