LLMを連動し、データベースを参照し、リマインドを徹底的に行うソフトウェア。

データベース一覧
メール(特筆すべきもののみを保持し、定期的に掃除する。MVPでは掃除機能なし。掃除する基準を設計する必要あり*TODO)
カレンダー(CalDavサーバーが既にあるため、それを使用)
Todoリスト(現在Googleのものを使っているため、それを使用)
リマインド状況
リマインド計画

動作機序

毎朝
新規メールを取得し特筆すべきもののみデータベースに記録
カレンダーの予定を1週間分取得
Todoリストの未完のものを取得
取得したデータ群をLLMに投げ、通知メッセージを生成
Discordのチャンネルに通知を送信

特殊動作
LLMの柔軟な判断をもとに、絶対に予定をど忘れしていたという事態を避けられるように通知をする
カレンダーの予定データベースには状態が分かれている。予定、準備、完了
予定は単にカレンダーに追加されている状態=忘れている可能性あり
準備はカレンダーに記録されている予定の準備が完了した状態=忘れずに準備が完了している
完了は完全に予定が終了し、無事終わった状態
追加で、リマインド状況データベースもある -> 後述

Todoリストは予定というよりタスクを記録する。締め切りのあるタスクは締め切りをカレンダーにも追加する。
タスクを忘れていないかどうかを定期的に確認する。
タスクは状態が分かれている。Todo, Ongoing, Done

リマインド状況は以下の目的で使用する。
人間は頻繁にリマインドされると鬱陶しく感じる。その癖にリマインドの頻度が低いとリマインドが弱いと逆切れする。
そのため、最適なリマインド間隔をLLMに判断させ、リマインドを計画する。
まず、初めて予定を通知するタイミングの判断を予定の追加を検知したタイミングで行う。
このタスクは時間がかかりそうだから最初の通知は一週間前に行う。このタスクは一日で終わりそうだから締め切りの3日前でいいだろう。
このタスクは一日あれば終わりそうだけど、予定が込み合っているから早めに通知しよう。
そういう判断をLLMが行い、リマインド計画に追加する。

リマインドをしたとき、Discordのチャンネルでユーザーが自然言語で反応するかもしれないし、反応しないかもしれない。
反応に応じてリマインド状況を更新する。
まず通知をしたときには反応なしとする。
承知した旨があったとしたら承知した旨を記録する。
次回のハートビートで通知計画を立てるタイミングでこの通知状況を確認し、無視を検知したら条件に応じて通知方針を判断する。
まだまだ先なら鬱陶しがられるのを避けるために次回通知を遅らせる。
もう締め切りが迫っているのに無視しているならうるさく通知する。

何が言いたいかというと、人間が鬱陶しがって無視しないが、必要な時にはうるさく通知してくれるツールが作りたい。
その判断をLLMにさせたい。


# 追加判断
### A. プロダクト・スコープ

- **利用者モデル:** 単一ユーザー固定か、将来のマルチユーザー対応を見据えるか
単一ユーザー固定。自分のためだけのツール。

- **MVP の成功基準:** 何が動けば「使える」と言えるか（例: 毎朝 1 回の通知 + 1 件のリマインド計画）
毎朝一回の通知
予定やTodoをDiscordから自然言語で追加できる。
予定を追加したらすべての予定に通知計画が存在している。
(すべての予定がDiscordから追加されるわけではない。定期的にサーバーと通信をして変更を検知する必要あり。また、すべての予定が通知必須なわけではない。)
リマインド計画の時間になったらリマインドが実行され、次の計画が立てられる。

- **対象外の明示:** モバイルアプリ、Web UI、複数 Discord サーバー対応など
モバイル、WebUI、複数Discordサーバー対応、複数Discordチャンネル対応、ユーザーログイン、使用者検知

### B. アーキテクチャ・実行モデル

- **プロセス形態:** 常駐デーモン vs cron / systemd timer vs 両方
Discordのメッセージを常に待機するため、デーモン
ただし、通知は計画に従ってハートビートする動作になるため、両方が好ましい可能性がある。
これについてはAIエージェントの判断を訊きたい。

- **「毎朝」の定義:** タイムゾーン、実行時刻、夏時間
JPT 朝8:00
- **「ハートビート」の間隔:** リマインド計画の再評価・無視判定をどの頻度で行うか
記述の通り、無視判定はデフォルトで真。次にシステムが何かしらでスキャンを始めたときに前回の通知からの時間を加味して、無視しているか、まだ見ていないだけかを判断する。この匙加減はLLMに任せる。
例、初回通知計画が1/1 15:00に立てられた。
1/1 15:00に通知が飛んだ。この時次回通知計画を立てる。
別のタスクの計画が16:00に実行され、別の通知が実行された。この時この通知動作をフックにしてリマインド状況を走査する。この時無視されている通知があることをシステムが検知する。
無視されている通知をすべてLLMにシステムが投げる。
LLMの匙加減にはよるが、例えば1/1 15:00に通知した予定は余裕があったとする。すると前回通知から一時間しかたっていないし、大学の講義中の可能性も全然ありうる。つまり、これは無視ではないと判断し、次回通知計画を早めたりはしない。
しかし、もしこの予定の締め切りが17:00だったとする。このタイミングで16:00で反応がないのは本当にまずいから次回通知計画を直近に動かす。
このような判断ができるシステムをMVPとする。

- **イベント駆動 vs ポーリング:** 予定追加の「検知」は CalDAV 同期時か、定期スキャンか
定期スキャン+Discordメッセージ受信時

- **MCP（`rust-mcp-sdk`）の役割:** LLM ツール呼び出し用か、外部連携用か
これはrigを使う。rust-mcp-sdkは古い。
LLMがツールを呼び出す時にここを叩く。LLMが直接APIを叩くことがないように、データベースやAPI出力をここでラップしてLLMに渡す。
